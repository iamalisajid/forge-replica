    Any web app URL → runnable full-stack code

    Observe the app.
    Rebuild the experience.

    An orchestrator that turns any web app URL into a new, independently runnable implementation: frontend, backend, database and migrations. It proves the result by running the same scenarios on the original and on the replica, with the replica cut off from the original.

    9stages
    2agent sessions
    2structured model calls
    1oracle: the original app
    INPUT

    A web app URL. Optional: scope hints, budget (USD and wall time), mutation policy (read-only or a test account) and a one-time operator login.

    OUTPUT

    A standalone repository: React frontend, Fastify API, PostgreSQL schema and migrations, seed data, tests, Docker Compose, exact run commands and a verification report bound to the commit.

    CONTROL PLANE · DETERMINISTIC PYTHONOwns stage order, budgets, artifacts, validation, retries and every pass/fail decision.

    Model work is limited to two Claude Agent SDK sessions (Explore, Build) and two structured-output calls (Extract interpreter, Specify). Agents propose; code verifies. Nothing an agent claims counts until the harness re-runs the check itself.

    Reconstruction boundary: A URL exposes rendered UI, network traffic, client storage and shipped client code — not backend source, the database or hidden server behavior. The system writes a new implementation of observed behavior, labels every claim observed, inferred or assumed, and reports what it could not observe. Support is decided per feature: real apps mix protocols, so some features can be rebuilt while others are declared out of scope.
    01 / Execution route

    Preflight → explore → cite → specify → prove → generate → build → verify.

    Green stages are plain code, blue stages are Claude Agent SDK sessions, violet stages are code wrapped around one structured-output call. Every arrow is a saved artifact; select a stage to open its details.

    FAILED CHECK → ROUTE → OWNER → RECHECK

    Two loops with separate budgets: the builder's inner loop (typecheck, build, scenarios, at most 2 rounds in v1) and the outer repair loop (routed by check type to Build, Specify or Explore; codegen bugs stop the run with a report). Each failure fingerprint gets one routed repair; if it returns, that branch stops and is marked partial.

    02 / Concurrency

    What runs in parallel, and what waits.

    Work runs in parallel only when it shares no inputs. Gates stay sequential, so a wrong spec is caught once instead of being multiplied across parallel workers.

    Always sequential

    Preflight before any model call · the pilot workflow through every stage before fan-out · Specify as one call, because entities and relations need one global view · the negative control after codegen and validation · merges, one slice at a time · the restart check after the scenarios that created its data · final Verify on the integrated commit.

    Limits are configuration

    --max-browsers (default 3) shares one rate limit against the original; --max-agents (default 2) stays under API rate limits, with backoff on 429; --max-stacks (default 2) protects local memory. Parallel sessions draw on one run budget through per-session caps, and the shared spec prefix is cached once before fan-out.

    05 / Artifact handoffs

    Who produces it. Who reads it.

    Artifacts are typed JSON files with a schema id, the hashes of their inputs, and the code, prompt and model versions that produced them. That makes resume, caching and invalidation mechanical.

    One responsibility per stage.

    Each stage is a function from typed input artifacts to typed output artifacts. The details below show what v1 builds and what is deliberately deferred.

    Normal codeAgent sessionCode + structured callSaved artifact
    Scope policy: With only a URL, preflight and the breadth pass propose a prioritized feature inventory. Features are built in priority order within the budget; everything else is reported as observed-but-not-built or not observed. Broad coverage is never presented as complete parity.
    ↑ Back to top

    Prove it on the original first.

    If acceptance tests come only from the model's own spec, a misread observation makes the test and the replica wrong together, and the replica still passes. Here every protected scenario must pass on the original app before it can judge the replica, and must fail on a build that is known to be broken.

    Recorded trace→Scenario with bindings→Non-vacuity check→3/3 on original→Passes on baseline, fails on rollback mutant→Protected + held out→Replica, no route to original

    Values come from the harness

    Every typed value is a fresh nonce bound at run time ({{uniq}}, {{created.id}}). Hardcoded strings or seeded rows cannot satisfy a scenario, and locators are scoped to the row or card that contains the nonce.

    Assertions must be able to fail

    Post-conditions are evaluated before the action on the original; assertions that already hold do not count. Each must also pass on the normal build and then fail, with an assertion, on a mutant that rolls back every write — at a step after its first write.

    Persistence is checked three ways

    Re-read in a fresh browser context (defeats client-only state), an effect check through the mapped operation (API on the original, API or database on the replica), and a full restart.

    Scenarios are data, not code

    A harness-owned interpreter reads scenarios.json. The original runs in its own process with credentials in memory only; the replica runner has none. Tests in the delivered repo are rendered for users and never executed by the harness.

    Repair the cause.

    A failing check does not always mean the builder is wrong. Each failure class has an owner, a rerun scope and a shortcut to avoid.

    Two loops, two budgets

    Inner loop: the builder iterates against typecheck, build and scenarios within max_turns and max_budget_usd. Outer loop: each failure fingerprint gets one routed repair, with at most 3 outer repairs per run under dollar and time caps.

    Fingerprint and stop

    A fingerprint is check id + error class + location. The same fingerprint after a repair stops that branch and records it as partial, with evidence, instead of looping.

    Hooks give feedback; hashes enforce

    The path guard rejects bad edits early, but the decision is made at Verify: protected files must match the codegen manifest and generated code must survive regenerate-and-diff.

    Invalidate by content hash

    Each artifact is keyed by its inputs, stage code, prompt and model versions. An upstream change reruns only what depends on it.

    Environment failures are not spec failures

    Expired sessions, rate limits and challenge pages are classified as environment failures with their own handling, so they never rewrite expectations.

    Held-out stays held out

    Repair dossiers show held-out failures only by category. A held-out scenario revealed during repair is retired and replaced.

    Isolate every zone.

    The explorer reads untrusted pages while holding a session; the builder writes and runs code. Each zone gets only the tools, network and secrets it needs. The Agent SDK's permission system is a permission gate, not a sandbox, so isolation comes from processes, containers and networks.

    Scope is not one session: the 4-hour session builds the core with the REST adapter and the auth pack.     Clean-start acceptance

    1. Fresh clone of the verified commit.
    2. docker compose up: database healthy, migrations applied to an empty database, app healthy.
    3. Drift check: migrations match the schema.
    4. Protected and held-out scenarios pass with no route to the original.
    5. Data-changing scenarios re-read in a fresh context and pass their effect checks.
    6. Restart and re-read.
    7. Functional, visual and unsupported results reported separately.
    Auth and external services: the replica has its own signup and login (auth pack); SSO originals get a local mock identity provider. Cloud services become local services in the same compose file: LocalStack for S3, Mailpit for email, stripe-mock for payments, WireMock for other browser-side APIs. Nothing is deployed and nothing calls the internet.

    Compared with the single-lane schedule above, this leaves roughly 30–40 minutes for debugging. The single-lane schedule stays the fallback if only one agent is available.

    Pilot first: every block is built and tested against one workflow — create → reload → edit → delete on issues. forge runs that pilot through every stage before expanding coverage, so a broken stage is found in minutes and for about a dollar.
    Cut order if behind: visual report → hygiene scans beyond the hash check → builder fidelity pass (keep fix-on-failure) → negative-control mutant → stability 3 runs → 2. Rows marked v1 elsewhere describe the first version's design; this order decides what lands inside the session. Never cut: recorded exploration, cited extraction, codegen, validation on the original, verification with no route to the original.

    Model and harness

    Output quality depends on both. The judgment stages — exploration choices, protocol interpretation, the spec and the builder — get worse with weaker models: lower coverage, more rejected citations, thinner specs, weaker fidelity and more repair rounds. A cheaper model can therefore cost more per verified workflow.

    The design limits the damage. Codegen, migrations, CRUD screens and every check are model-independent. Citations, integrity checks and the oracle turn weak output into visible failures instead of false passes. Structured outputs keep JSON valid on any model.

    v1 runs one strong model, claude-opus-5-5, with effort tuned per stage, through the Claude Agent SDK harness rather than a hand-rolled loop. The model is per-stage configuration recorded in every artifact. A cheaper model replaces it only where the benchmark shows the same held-out pass rate at lower cost per verified workflow.

    Key decisions.

    D1

    Deterministic control plane

    Decision: Python orchestrates; two agent sessions and two structured calls do the judgment work.

    Rejected: one autonomous “clone this” agent — kept as the baseline to beat.

    D2

    Evidence first

    Decision: traffic and the accessibility tree are primary evidence; the harness records, agents choose actions.

    Rejected: inferring models from screenshots and page text, as the prototype did.

    D3

    One operation format

    Decision: adapters plus an interpreter whose every citation is checked in code.

    Rejected: REST-only extraction; trusting model interpretation without citations.

    D4

    Flat spec, rendered contract

    Decision: the model writes a flat AppSpec; code renders OpenAPI, the Prisma schema and a working CRUD UI.

    Rejected: model-written OpenAPI (structured outputs cannot express it), model-written migrations, agent-chosen stacks.

    D5

    The original is the oracle

    Decision: scenarios must be non-vacuous, pass 3/3 on the original and fail on a broken mutant before they judge the replica.

    Rejected: acceptance tests derived only from the spec, which grade the model against itself.

    D6

    Isolation by zone

    Decision: v1 uses a real-path guard, sandboxed checks and a stopped original; hardening moves the agent loop into a container.

    Rejected: treating folders or permission rules as a sandbox.

    D7

    Honest scope

    Decision: preflight assigns support per feature; limitations are part of the output.

    Rejected: promising parity with any app.

    D8

    Measure, don't assert

    Decision: benchmark targets with ground truth, held-out tests and a baseline.

    Rejected: judging the system by one demo.

    D9

    Models are configuration

    Decision: one strong model with per-stage effort; the model id is part of every artifact's cache key; a cheaper model is adopted per stage only when the benchmark shows no loss.

    Rejected: choosing models by token price; hard-wiring a model into prompts or code.

    D10

    Parallel where independent

    Decision: pilot first, then fan out; codegen alongside validation; parallel browsers, stacks and checks under shared limits; slices behind a merge queue.

    Rejected: parallel from the start (a wrong spec is multiplied), or strictly sequential (wall time).
